      Bubble sort

      Repeatedly compares neighboring values and swaps them if they are reversed. An early-exit check stops when a pass makes no swaps. Average/worst time: O(n²); extra storage: O(1).

      Insertion sort

      Builds a sorted prefix by shifting larger values right and inserting the next value. Efficient for small or nearly sorted inputs. Average/worst time: O(n²); extra storage: O(1). The visualizer stores snapshots separately for playback.

      04 / COMPRESSION BENCH

      Smaller isn't magic.

      LOSSLESS / LOCAL ONLY

      Computers store text, pictures, audio, and programs as bytes. Compression represents those same bytes more efficiently by finding patterns. Follow the journey from raw data to repeated runs, dictionary references, compact binary codes, and a real ZIP.

      01 / Everything starts as bytes

      A bit is 0 or 1. Eight bits make a byte, with 256 possible values. The same byte can be displayed as decimal, hexadecimal, or binary: these are different notations, not different amounts of data.

      03 / Remember earlier patterns: dictionary references

      RLE cannot shorten ABCABCABC because adjacent bytes differ. A dictionary method can write A B C, then say “go back 3 bytes and copy 6.” It works on pixel rows, audio patterns, or any repeated bytes—not just text.

      This simplified LZ-style lesson uses the first 256 bytes of the selected sample, a 64-byte history, and matches of 3–34 bytes. A literal costs 9 bits (a tag + 8 data bits); a reference costs 12 (a tag + 6 distance bits + 5 length bits). These are teaching-format costs, not actual DEFLATE output. Copies may overlap: the decoder can reuse bytes it just produced.

      04 / Give frequent symbols shorter codes

      Ordinary byte storage spends 8 bits on every value. Huffman coding builds a prefix-free code: common symbols get short codes and no full code is the start of another. A decoder can tell where each code ends without separators.

      Photos and recordings

      Raw pixels and PCM audio can contain structure a lossless compressor can exploit. PNG already uses lossless compression, so zipping a PNG often saves little. JPEG, MP3, and many video formats use specialized compression, often lossy; ZIP cannot restore details those formats already discarded.

      Why not compress forever?

      No lossless compressor can make every possible input smaller: there are fewer short byte strings than long ones. Random-looking data often stays the same size or grows. Encryption normally removes useful visible patterns; compress before encrypting when appropriate, not to “undo” encryption.

      06 / Build a real ZIP

      Choose up to 20 files, 10 MB combined. ZIP is a container; DEFLATE compresses each entry using repeated byte sequences and compact codes. Already-compressed photos, music, or archives may not shrink. Filenames are made portable and duplicates receive suffixes. No folders, extraction, encryption, or passwords.

      Download ZIP

      Ready. Choose local files to begin. Selecting files does not execute them or upload them.

        Lossless means reversible

        Decoding reproduces the exact original bytes. RLE expands count / value pairs. DEFLATE uses back-references and Huffman coding. Unlike lossy photo or audio encoding, neither deliberately discards information.

        ZIP is a container

        A ZIP bundles separate entries with filenames, metadata, and a central directory. Each entry can be compressed or stored. Metadata costs space, so tiny files can produce a larger archive even when their payload compresses.

        Integrity is not secrecy

        CRC-32 detects accidental corruption; it is not cryptographic authentication. Compression is not encryption. A ZIP from this lab is readable by anyone who receives it, and does not establish that its contents are safe.

        01 / Hashing: a fingerprint, not a lock

        SHA-256 turns any bounded message here into 256 bits. Identical input bytes always produce the same digest. Changing one character can flip many output bits, even though the hash stays the same length. You cannot “decrypt” a hash to retrieve the message.

        02 / Encryption: lock, unlock, and detect tampering

        AES-GCM is authenticated encryption. It hides the plaintext and produces an authentication tag. Decryption releases plaintext only when the key, nonce, ciphertext, and tag agree. A wrong key or altered byte causes verification to fail.

        Start by generating a key. This is a random AES-256 key, not a password.

        Each encryption uses a fresh cryptographically random 96-bit nonce and a 128-bit tag. Never reuse a nonce with the same AES-GCM key. Randomness is practical here, not a uniqueness guarantee for an unbounded production system. The test buttons change only a copy or use a separate key; your original stays available. A new key discards the old ciphertext.

        Clearing removes the lab's references and visible inputs; JavaScript cannot promise secure memory erasure. Reloading or leaving the page also discards the session. Non-exportable keys cannot be exported through Web Crypto, but that does not make this page safe against a compromised browser or malicious same-origin scripts.

        Encoding ≠ encryption

        Hex and Base64 change representation and need no secret to reverse. Hex uses two characters per byte. Compression exploits patterns; it does not keep data secret. Ciphertext is usually not usefully compressible.

        A hash needs trust, too

        A file hash helps detect changes if the expected digest came from a trusted source. Anyone can hash a message. Authenticating its sender needs something else, such as a keyed MAC or digital signature; this studio does not implement signatures.

        Authentication has limits

        An AES-GCM tag checks data using a shared secret key. It does not identify a person, prevent replay by itself, or solve key exchange. Real secure messaging needs a complete, reviewed protocol—not just an encryption function.
